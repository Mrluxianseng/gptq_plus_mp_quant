## 为什么旧调参结果不能直接使用

2026-08-08 `full_block` 和 2026-08-11 `single_linear` 两轮都用快速代理曲线直接决定
正式 LR。代理配置只量化前约四分之一层，并使用 `blocksize=256`、
`backward_samples=16`、`loss_slide_window=false`。正式配置则量化完整模型并使用
`w_groupsize=128`、`blocksize=128`、`backward_samples=32`、
`loss_slide_window=true`。2026-08-12 的全模型对照已经实测到代理排序会反转，因此旧代理
LR 只能作为历史信息，不能作为本轮最终选择依据。

此外，旧流程一度把相邻点 KL 差距小于 2% 当作停止条件。这个规则会在平坦区过早停止，
无法证明已经取得 LR 的低侧/高侧 bracket。新流程仅把 2% 用于报告 near-optimal
plateau，不再作为收敛门禁。

## 冻结配置与公平性

- calibration：WikiText-2 train，固定 256 条 × 2048 token。由于 static cache key 包含
  `global_loss_bsz`，V4/V5 对每个 config 选择两侧历史成功值中较小的共同
  `global_loss_bsz`，两分支读取同一套物理 static/reference/token cache；plan 对
  calibration token tensor 计算 SHA-256，并强制同一模型的两侧 hash 完全相等。
  超大 static/reference cache 记录精确路径、cache key、大小和 `mtime_ns`，每次启动前
  复核；consumer 强制 `require_static_cache_hit=true`、
  `require_reference_cache_hit=true`。
- 随机性：`seed=1`、`rotation_seed=0`、`refresh_seed=0`；
  `REALQ_DETERMINISTIC_SDPA=1`、`CUBLAS_WORKSPACE_CONFIG=:4096:8`、
  `PYTHONHASHSEED=0`、`NVIDIA_TF32_OVERRIDE=0`。
- 正式一致 profile：完整模型，`w_groupsize=128`、`nsamples=256`、
  `seq_len=2048`、`blocksize=128`、`backward_samples=32`、
  `backward_bsz=32`、`loss_slide_window=true`。禁止出现 `quant_stop_layer`。
- V4/V5 主 campaign 依据 2026-08-08 二十设定冻结记录，所有模型/设定均固定
  `a_loss_ratio=1.0`。Qwen3-4B 的 `.95` 只在独立消融中与 `1.0` 各自完整调参；
  只有 `.95` 在四个正式配对中全部赢 Exact KL 且不恶化 PPL 才采用，否则按
  用户要求回退 `1.0`。
- W4A16/W3A16/W2A16 固定 reverse-cosine（CLI 值 `cosine`）；W4A4KV4 固定
  constant LR（CLI 值 `none`）。本轮不在调参中切换 scheduler。
- `final_layer_grad_lr` 不随本轮 `grad_lr` sweep 改变：模型 ≤4B 固定 `1e-5`，模型 >4B
  固定 `1e-6`。因此 `grad_lr=0` 只关闭普通 block 的更新，最后一个 transformer block
  仍执行分支特有的 KL Block-GD；它是每个分支自己的曲线端点，不是跨分支 physical zero。
- V1 曾按分支沿用不同 `global_loss_bsz`，配对门禁证明不公平后已作废。
  V4/V5 对每个 config 取两分支历史成功值中较小、且已有成功 static cache 的
  共同 `global_loss_bsz`，两分支使用同一个物理 static/reference/token cache。Qwen3-32B
  唯一数值例外仍是已授权的
  `hessian_accum_bsz=32`，其他模型保持 64；若后续真实 OOM，只允许按用户授权降低
  Hessian accumulation batch，不能再让两侧 static/global-loss profile 分叉。
- 每个 `branch/config` 最多 20 次真实 launch；OOM、平台失败和指标解析失败单独分类，
  均不能当作“高 LR 变差”的证据。
- 每个 trial 保存完整精度 LR、命令、命令 SHA-256、代码快照、协议 fingerprint、物理
  GPU UUID、Exact KL、PPL、耗时和日志路径。LR 目录名使用全精度值的 SHA-256 前缀，
  避免历史上 `.8g` 截断造成的候选碰撞。

## 新学习率选择协议

1. 先只测 20 个 config 的两分支 `grad_lr=0`，共 40 个完整模型曲线端点。由于冻结的
   `final_layer_grad_lr` 仍为正值，两分支结果允许不同；公平性门禁是命令除分支 flag/
   output 外一致、同一物理 cache、相同 seed，而不是跨分支指标相等。
2. 端点全部检查后，另写不可变 manifest，只放行 `1e-7`。后续候选也逐批从低到高
   放行；不会预先机械提交 `1e-6、1e-5、1e-4`。若当前点改善才继续向高侧走；若首个
   正 LR 已变差，则在 0 与 `1e-7` 之间继续测更小正 LR。
3. agent 每批查看 Exact KL 后再放下一小批。若当前最大 LR 仍改善，按 log 空间继续向
   高侧扩展；只有同一组出现两个成功、实测且比 incumbent 更差的高侧点，才视为取得
   高侧证据。OOM/基础设施失败不算。
4. 在最优点两侧用几何中点细化，直到局部正 LR bracket 宽度不超过 0.30 dex
   （约 2 倍）。`lr=0` 是独立 control，不参与 log 插值。
5. 最终前两名候选在同一分支内至少各精确复跑一次。同 LR 两次完全一致时 noise floor
   为 0、两次即可；若任一候选的前两次 Exact KL 不同，则该候选必须补第三次，再用
   median 与 range/MAD 判断。差异没有超过重复噪声时报告 tie，并保守选择较小 LR。
   确定性判断只比较同一分支、同一全部参数的复跑，不比较两个算法分支。
6. 选定 LR 后重新跑一次完整正式量化并保存 checkpoint；再从 checkpoint 测 WikiText-2
   PPL、十项 QA 和 GSM8K/MATH-500/HumanEval+ 三项推理。调参 trial 不承担正式结果。

上述选择规则已实现为独立的只读分析器：它只能读取 trial 结果、给出下一候选建议，
不能自行启动任务；只有 40 组全部同时通过两个高侧点、0.30 dex bracket、top-2 同分支
复跑和 noise-aware tie 门禁时，才允许原子发布 `selections.json`。V4 保留 V2/V3 经过
修正的成对 physical-cache command diff 与混合模型调度，并固定 all-one a-loss；
Q32 V5 只用等价显存实现接续 V4 的 zero/失败证据。选择器额外验证：端点后首个正候选
固定为 `1e-7`；若它已
劣于端点，则向 `1e-8` 细化 physical-zero boundary，而不是继续机械扩大 LR。
